## 1. Redundancy: what happens when one endpoint dies

"Endpoint" means two different things here, and the answer differs.

### 1a. An upstream source dies (e.g. MeteoSwiss, SBB API, PXWeb)

**What exists today (good, `src/core/http.ts`):**

| Mechanism | Behaviour |
|---|---|
| Per-host circuit breaker | 5 consecutive transient failures → fail fast for 30 s, then one half-open probe |
| One retry | 600 ms backoff (or `Retry-After` ≤ 2 s); POSTs with a body are not retried on timeout |
| Stale-while-revalidate | Serve cached data up to 6 × TTL while refreshing in background |
| Stale-if-error | If the source fails, serve the old body up to **24 × TTL**, marked `cache_status: "stale"` |
| Single-flight | N concurrent misses → 1 upstream call |
| Per-host concurrency cap | 8 in-flight per host; one slow source can't starve the rest |
| Isolation | Each module is independent; one dead source never takes down other tools |
| Visibility | `check_source_health` / `/v1/health/sources` expose breaker state to agents |

**What is missing — this is *resilience*, not *redundancy*:**

1. **Only 2 of ~25 sources have a real alternate endpoint.**
   - `earthquakes`: `eida.ethz.ch` → `arclink.ethz.ch` (plain HTTP — see R-16).
   - `companies`: ZefixPublicREST → keyless ZefixREST, but **only on 401/403**, not on outage.
   - Every other source is a single point of failure. With a cold cache, a dead source = an error.
2. **Stale data only exists if the cache is warm, and the cache is in-memory.** Every
   restart/deploy wipes it, so stale-if-error protects nothing in the minutes after a deploy —
   exactly when you are most likely to discover a broken upstream.
3. **Stale windows are tied to TTL, not to usefulness.** Transport (TTL 30 s) can be stale for
   at most 12 min; population (TTL 24 h, changes yearly) for 24 days. Neither is a deliberate
   choice.
4. **429 / `Retry-After` is not respected by the breaker.** A 429 with `Retry-After: 60` is
   not retried (good) but the breaker keeps sending traffic until 5 failures accumulate, then
   only backs off 30 s. That is the pattern behind the current PXWeb canary failure and is the
   fastest way to get the egress IP blocked.
5. **No static fallback for slow-changing reference data** (population, legal forms list,
   canton list, federal holidays, NABEL stations) that could ship inside the package.

### 1b. The hosted Swissyphus endpoint dies (`/v1/*`, `/mcp`)

**Today: no redundancy.** One VPS → one Caddy → one Node container → one `keys.json` on a
local Docker volume (`deploy/docker-compose.yml`). If the VPS, its disk, its DC, or the
process dies, the whole hosted API and remote MCP are down. Mitigations in place are recovery,
not availability: `restart: unless-stopped`, container healthcheck, graceful drain, a nightly
backup (off-site copy is "recommended", not automated), an external uptime check (manual setup).

Recovery-point: up to **24 h** of new keys (nightly backup) + up to **30 s** of usage
(in-memory flush). Recovery-time: manual (new VPS, restore tarball, DNS change).

Mitigating fact: **local users (`npx`, `.mcpb`, stdio) are unaffected** — each runs its own
instance. Only hosted customers depend on the VPS. That matters for the commercial story (§2):
anything you *sell* is the hosted path, and that path currently has the weakest availability.

Multi-replica is blocked by in-process state (cache, rate limits, keys, usage) — fully
specified as SCALE-1/3/4/5 in [`SCALING.md`](SCALING.md).

## 2. Licensing & commercialisation

### 2a. Software

- **MIT** (`LICENSE`, copyright "Swissyphus contributors"). Anyone — including a competitor —
  may fork, host and sell it. There is no licence moat; the only defensible assets are the
  **name/brand, the hosted service's reliability, and upstream relationships** (credentials,
  written permissions).
- No CLA/DCO. Fine while you are the sole author; if outside contributions arrive and you might
  ever relicense (e.g. open-core), add a DCO now.
- Name is not yet claimed on npm (BACKLOG #7a) and the repo is still private (BACKLOG #0).

### 2b. Commercial model (as designed)

From README + BACKLOG #6: hosted API with Anonymous / Free / Pro / Enterprise tiers, metering
**on**, billing **off**, everything free during "onboarding". No payment integration, no terms
of service, no SLA definition, no DPA template. "Enterprise: on-prem, SLA, DPA" is advertised
but there is nothing behind it, and §1b means no SLA could be honoured today.

### 2c. Data licences — the real constraint on charging money

You are not selling the data (most of it is free OGD); you are selling **normalisation,
attribution, reliability and one integration point**. That only works if every source permits
hosted/commercial redistribution. Status per [`docs/outreach/`](outreach/README.md):

| Source | Commercial-hosting status | Blocker? |
|---|---|---|
| MeteoSwiss forecast (`app-prod-ws.meteoswiss-app.ch`) | Undocumented app back-end, **no terms** | 🔴 yes — migrate to OGD STAC |
| transport.opendata.ch | Community API, **~1000 req/day fair-use guideline**, one egress IP for all customers | 🔴 yes — won't survive real traffic |
| ZEFIX keyless (`ZefixREST`) | Web-app internal back-end | 🔴 yes for paid tier — need FOJ credentials |
| SLF avalanche / IMIS | Unconfirmed for commercial use | 🟠 email not sent |
| SRF news | RSS terms personal/non-commercial (summaries already dropped) | 🟠 email not sent |
| existenz.ch (hydrology, weather history) | Private third-party proxy | 🟠 email not sent; go direct |
| OpenHolidays | ODbL (share-alike) — register now correct | 🟢 compatible if attribution + ODbL notice kept |
| opendata.swiss datasets | Each dataset has its own terms; some are `terms_by_ask` (commercial use needs permission) | 🟠 surface the flag per result (R-17) |
| swisstopo, SNB, Fedlex, BFS, Parliament, Alertswiss, SED | Swiss OGD / public, attribution | 🟢 |

**All five outreach emails are still "not sent".** They are the long pole for any paid tier.

### 2d. Recommendation

1. Keep **MIT** for the server (adoption is the point; the data is free anyway).
2. Monetise the **hosted service**: uptime SLA, higher limits, official-credential sources,
   support, DPA. Do *not* charge for any tool backed by a 🔴/🟠 source until it is resolved;
   gate those modules off in the paid deployment via the existing `--modules`/preset mechanism.
3. Add the missing commercial paperwork: Terms of Service + AUP, SLA definition (start at
   99.5 % monthly, which needs §1b fixes), DPA template (nFADP + GDPR SCCs), imprint.
4. Register the name/mark ("Swissyphus") if you intend to sell under it. Have someone check the
   🇨🇭/Swiss-cross usage against the Coat of Arms Protection Act (WSchG) so the service is not
   read as an official federal offering.

## 3. Requirements & improvements (prioritised)

Legend: 🔴 must before charging money · 🟠 should before 1.0 · 🟡 later. Size S ≤ 1 day,
M ≤ 1 week, L ≤ 1 sprint.

### Upstream redundancy

| # | Requirement | Pri | Size |
|---|---|---|---|
| R-1 | **Honour 429/`Retry-After` in the breaker**: on 429 open the host's circuit for `max(Retry-After, cooldown)` immediately instead of counting to 5. Add exponential cooldown (30 s → 60 → 120 … cap 10 min) for repeated half-open failures. Fixes the PXWeb canary pattern. | 🔴 | S |
| R-2 | **Persistent last-known-good store**: write successful responses for selected sources (reference data, forecasts, bulletins) to `SWISSYPHUS_DATA_DIR/lkg/` and load on start, so stale-if-error survives restarts/deploys. Bounded by bytes; never for keyed/personal data. | 🔴 | M |
| R-3 | **Per-source max-stale policy** in `SourceManifest` (`maxStaleSeconds`) replacing the global 6×/24× factors: e.g. transport 5 min, weather 6 h, avalanche 24 h, population 400 d, law 30 d. Envelope already carries `staleAgeSeconds`. | 🟠 | S |
| R-4 | **Generic multi-endpoint support**: `SourceManifest.endpoints: string[]` with preferred-endpoint memory (generalise what `earthquakes.ts` does), plus `ZEFIX` failing over to keyless on 5xx/timeout, not only 401/403. | 🟠 | M |
